# Serve data over OPTIMADE

This example starts with CIF files and a JSON table of results, stores both in
SQLite, and serves two OPTIMADE entry types: `structures` and `_httk_records`.
Each result has a numeric formation energy and a relationship to its structure.
This follows the typed-result pattern used by
[altermagnets](https://github.com/Anyterial/altermagnets): application dataclasses
hold the results, property definitions describe their meaning, and *httk-serve*
serves the store directly.

Use Python 3.12 or newer and install the three modules (also included in the
`httk2` metapackage):

```bash
python -m pip install 'httk-atomistic[default]' 'httk-store[db]' httk-serve
```

## Prepare the input files

Create this directory; `results.sqlite` will be generated by the import:

```text
materials/
  api.py
  results.json
  cifs/
    NaCl.cif
    MgO.cif
```

explicitly, with the identity symmetry operation.

Save this as `results.json`. These are **invented demonstration energies** in
eV per atom, not calculated or measured values. Each `cif` names a file relative
to `cifs/`; `sample` distinguishes determinations, so several results can refer
to the same CIF.

```json
[
  {"sample": "nacl-demo", "cif": "NaCl.cif", "formation_energy": -1.2},
  {"sample": "mgo-demo", "cif": "MgO.cif", "formation_energy": -0.8}
]
```

## Define, import, and serve the records

Save the following as `api.py`. `Result` is a frozen application record, and
`ResultEntry` binds it to the `_httk_records` endpoint. The property definition
and projection explicitly make its energy readable, filterable, and sortable.
The local field `formation_energy` is published as
`_httk_custom_formation_energy`: custom OPTIMADE attributes need a provider
prefix, and `_httk_custom_` keeps this example separate from curated property
definitions.

```python
import argparse
import json
from dataclasses import dataclass, field
from pathlib import Path
from typing import Annotated, ClassVar

from httk.atomistic import StructureEntry, UnitcellStructureRecord, UnitcellStructureView
from httk.core import EntryTypeDefinition, PropertyDefinition, load, load_entry_type_definition
from httk.core.data_records import RECORDS_DEFINITION_ID
from httk.core.register import register_entry_family, register_entry_record
from httk.core.storage import (
    IdentitySkip,
    Indexed,
    StorageInfo,
    StoredPropertyProjection,
    Unique,
    WeakLink,
)
from httk.serve.optimade import serve
from httk.store import EntryIdScheme, SqliteStore


@dataclass(frozen=True)
class Result:
    """One result in eV/atom, associated with a structure lineage.

    :param sample: Label distinguishing this determination from others.
    :param formation_energy: Formation energy per atom, in eV.
    :param id: Public lineage ID, assigned by the store.
    :param immutable_id: Revision ID, assigned by the store.
    """

    sample: str
    formation_energy: float
    id: Annotated[str | None, IdentitySkip(), Indexed()] = field(default=None, compare=False)
    immutable_id: Annotated[str | None, IdentitySkip(), Unique()] = field(
        default=None, compare=False
    )

    __httk_storage__: ClassVar = StorageInfo(
        storage_name="example_results",
        identity_name="example.result",
        links=(
            WeakLink(
                "structure",
                target=UnitcellStructureRecord,
                exposed_relationship=True,
                role="subject",
            ),
        ),
    )
    __httk_stored_properties__: ClassVar = {
        "_httk_custom_formation_energy": StoredPropertyProjection(
            response=lambda record: record.formation_energy,
            query=lambda context, operator, value: context.compare(
                context.field("formation_energy"), operator, context.constant(value)
            ),
            sort=lambda context: context.field("formation_energy"),
        ),
    }


class ResultEntry:
    """The application's typed results, served as _httk_records."""

    type = "records"
    definition_id = RECORDS_DEFINITION_ID

    @classmethod
    def entry_type_definition(cls) -> EntryTypeDefinition:
        """Describe the result quantity and its units to API clients."""
        return load_entry_type_definition(cls.definition_id).extended(
            {
                "_httk_custom_formation_energy": PropertyDefinition.from_simple(
                    "_httk_custom_formation_energy",
                    description="Formation energy per atom relative to elemental reference phases.",
                    fulltype="float",
                    unit="eV",
                ),
            }
        )


register_entry_family(
    name="example-results", family=f"{__name__}:ResultEntry", definition_id=RECORDS_DEFINITION_ID
)
register_entry_record(name="example-result", record=f"{__name__}:Result", family="example-results")


def open_store() -> SqliteStore:
    """Open the database using the same layouts for import and serving."""
    return SqliteStore(
        Path(__file__).with_name("results.sqlite"),
        entry_records={StructureEntry: UnitcellStructureRecord, ResultEntry: Result},
        entry_ids=EntryIdScheme("example", "1"),
    )


def ingest(store: SqliteStore) -> None:
    """Load the local CIF files and their JSON results in one transaction.

    :param store: The destination store.
    """
    root = Path(__file__).parent
    rows = json.loads((root / "results.json").read_text(encoding="utf-8"))
    with store.transaction():
        for row in rows:
            structure = UnitcellStructureView(load(root / "cifs" / row["cif"]))
            sid = store.save(structure)
            stored = store.fetch(UnitcellStructureRecord, sid)
            store.save(Result(row["sample"], row["formation_energy"]), links={"structure": stored})


if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("action", choices=("build", "serve"))
    args = parser.parse_args()
    with open_store() as store:
        if args.action == "build":
            ingest(store)
        else:
            serve(store, port=8080)
```

`load()` reads a CIF's asymmetric unit; `UnitcellStructureView` expands its
symmetry to a unit cell when the store needs it. The store preserves the exact
structure values; OPTIMADE presents numeric coordinates as JSON numbers.
The JSON energy here is explicitly stored as a floating-point number.
`identity_name` pins the result type's content identity, so running `api.py`
and importing it from another script use the same persistent layout.

`WeakLink("structure", ...)` gives local records the accessor
`record.links.structure` (the API spells **links** in the plural). This is a
mutable association to the structure's lineage, and follows its latest
revision. It is suitable for this curated result table. For calculation
provenance that must pin the input revision, use a `StrongLink`/`product_of`
edge, as the calculation records in `altermagnets` do; see the
[provenance guide](https://docs.httk.org/httk-store/dev/main/details/db-relationships.html#strong-links-provenance-edges).

From the `materials/` directory, import once and then start the server:

```bash
python api.py build
python api.py serve
```

The import commits as one transaction: a missing or unreadable CIF rolls back
the batch. Repeating an unchanged import deduplicates the structures and
results. A changed result is a new entry, not an implicit revision of an old
one. `sample` is retained locally to distinguish determinations but is not
published by this example's property map. To publish other JSON columns, add
their typed dataclass fields, property definitions (including meaning and
units), and projections in the same way; use a fresh example database after
changing the stored layout.

Serving reads the persisted database without reimporting the source files.
Filters and pagination run against SQLite. The `with` block closes the store
when the development server stops. For an ASGI deployment,
`create_asgi_app(store)` supplies the application; the deployment owns and must
close the store. The API needs a running Python service, even if its companion
website is published on a static host such as GitHub Pages.

## Query the API and include the linked structures

In another terminal:

```bash
curl http://127.0.0.1:8080/v1/info/_httk_records
curl http://127.0.0.1:8080/v1/structures
curl --get http://127.0.0.1:8080/v1/_httk_records \
  --data-urlencode 'filter=_httk_custom_formation_energy < -1' \
  --data-urlencode 'include=structures' \
  --data-urlencode 'response_fields=_httk_custom_formation_energy'
```

The last request selects the NaCl result. Its `data` item has the following
shape (IDs shown for a fresh database); the full response also has an
`included` array containing the linked `structures` resource and its lattice,
sites, species, and formula:

```json
{
  "id": "example-1-1",
  "type": "_httk_records",
  "attributes": {"_httk_custom_formation_energy": -1.2},
  "relationships": {
    "structures": {
      "data": [{
        "id": "example-1-1",
        "type": "structures",
        "meta": {"_httk_label": "structure", "role": "subject"}
      }]
    }
  }
}
```

IDs are scoped by entry type: the result and structure can have the same ID
string and still be different resources. Fetch an individual result at
`/v1/_httk_records/<id>` or a structure at `/v1/structures/<id>`.

The wire relationship is named `structures`, after the target entry type;
the local link name `structure` is preserved as `meta._httk_label`. A filter
such as `structures.elements HAS "Na"` on `/v1/_httk_records` selects results
through their linked structure. `/v1/info/_httk_records` describes the custom
energy property, its unit, and its sorting support.

## Query the same data from Python

For a local query, save this as `query.py` beside `api.py` and run
`python query.py`:

```python
from api import Result, open_store
from httk.atomistic import UnitcellStructureView

with open_store() as store:
    search = store.searcher()
    record = search.variable(Result)
    search.add(record.formation_energy < -1)
    for row in search.results(
        energy=record.formation_energy, structures=record.links.structure
    ):
        for structure in row.structures:
            print(UnitcellStructureView(structure).formula, row.energy)
```

```text
ClNa -1.2
```

From a separate process while the server is running, query the same relationship
over HTTP with `OptimadeStore`:

```python
from httk.atomistic import UnitcellStructureView
from httk.store.optimade import OptimadeStore

with OptimadeStore("http://127.0.0.1:8080") as store:
    search = store.searcher()
    record = search.variable(store.entry_type("_httk_records"))
    search.add(record._httk_custom_formation_energy < -1)
    for row in search.results(
        energy=record._httk_custom_formation_energy,
        structures=record.links.structures,
    ):
        for structure in row.structures:
            print(UnitcellStructureView(structure).formula, row.energy)
```

```text
ClNa -1.2
```

Local queries use the declared dataclass field and link names;
remote queries use the published attribute and relationship names.
